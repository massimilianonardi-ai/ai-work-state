# AI-Workflow — architecture-disclosure regression and corrective rules

Source: user observation of rsudo APISIX development; supported by archived development snapshots 0015, 0016, 0017 and m-rsudo commits, 2026-11-23.

Failure: The instruction to use the same simplicity and methodology as the rsudo Keycloak wrapper while consulting APISIX legacy code was materially ambiguous. The assistant recreated approximately 35 legacy-like public functions without making the architectural decision explicit before coding. Only after the user rejected that design did it deliver the minimal two-function API.

Evidence: m-rsudo commit 73b90295 implemented the broad API; 6c14698b replaced it with rest/key; HEAD 52dc0c4 documents the revised interface and passing CI. No live APISIX verification was observed. No proof of the model's subjective motivation; ease-of-generation bias is a hypothesis.

Approved workflow correction: AI-Workflow rules commit 30af690c. In a new implementation or material redesign, present a *complete, single, material architecture decision synthesis* before code: confirmed/inferred and approved/proposed requirements, public API, architecture, major technical strategy, inspiration/legacy treatment, alternatives and rationale, security/compatibility, exclusions and verification. Ask the operator about conflicting consequential interpretations, not routine engineering details. Rank approaches by project and product quality, not assistant convenience. One architectural approval, not microapprovals.

Review checkpoint for future evaluation: Did the assistant inspect the actual code? Did it explicitly compare plausible architectures? Were implicit consequential decisions visible and approved before the first code write? Was the final choice demonstrably the most suitable for the task? Did it autonomously write and verify code after authorization?

No changes to m-rsudo or the development chat; all updates confined to ai-workflow rules and this separate validation conversation.
