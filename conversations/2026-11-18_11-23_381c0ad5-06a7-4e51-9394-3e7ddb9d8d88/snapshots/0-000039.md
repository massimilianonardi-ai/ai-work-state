# AI-Workflow — Progressive Design & Execution (proposal 2026-11-23)

**Status:** collaborative design candidate, not yet user-approved for deployment in rules. Do not apply as an established workflow until a real approval and rule revision occur. Source: user's idea to balance human decisions against assistant autonomy using concise sequential formalization; assistant's reviewed proposal in this chat (branch 0, checkpoint 39).

## Core principle
Maximize autonomous execution **inside explicitly formalized boundaries**; involve the operator only when defining or changing those boundaries. Formalize one abstraction level at a time to focus analysis, reduce unjustified architectural leaps, prevent module-responsibility leakage and prepare linear implementation. Avoid turning every technical detail into an operator approval.

## Candidate progression
1. Outcomes and scope: desired results, actors, project context, limits/exclusions, nonnegotiable constraints. Operator validates.
2. Requirements: functional and nonfunctional, compatibility, invariants, integration/deployment conditions. Operator decides material ambiguity.
3. Use cases and observable acceptance: representative positive/negative scenarios, inputs/outputs and expected results. Operator validates outcomes.
4. Overall architecture: component boundaries, existing products, reuse vs build, major alternatives, choice rationale. Operator validates consequential decisions.
5. Component contracts: ownership, exclusions, interfaces, dependencies, data and control flow, state, failures, side effects. Assistant details; escalate only architecture changes.
6. Code-level design: classes, functions, parameters, algorithms, flowcharts/pseudocode, state machines when justified. Technical choice is assistant-owned.
7. Detailed tests: use-case-linked minimal representative tests, test boundaries/doubles, integration and E2E evidence; include meaningful failures without speculative suites.
8. Execution plan: ordered work, dependencies, risk-first checks, first viable vertical slice, artifact/commit boundaries, exit criteria and fallback/rollback when needed. Operator approves exceptional external effects and material changes.
9. Autonomous execution: code, checks, self-review for unnecessary complexity/incorrect ownership and correction.
10. Execution supervision: compare plan and actual product revisions, detect drift, wrong module responsibility, gratuitous complexity, inefficient retries and missing evidence. Independent chat can review fixed target checkpoint and Git SHA. Results: continue/correct/suspend; no silent edits to target or spec.
11. Acceptance/handoff: user-relevant observed behavior, disclosure of untested conditions, final decision and restart info.

## Three checkpoint types
- **Decision gate:** human approves results/requirements/contract/major architecture and significant authority/risk changes; grouped at meaningful milestones, not per function or commit.
- **Technical quality gate:** assistant verifies coherent schema, ownership, testability, actual code/evidence at each relevant abstraction. No human micro-approval.
- **Supervision gate:** independent or internal reviewer audits execution, against a pinned plan/spec revision and verified artifacts. Not equivalent to every-turn Git persistence.

## Adaptive depth
- Simple task: combine levels into a compact specification with main path, ownership, a short plan and minimal tests.
- Medium task: explicit component contracts, code schemas, significant flows and structured milestones.
- Complex/high risk: deeper nested designs, states/invariants, failure flows, versioned execution plans and independent review.
Depth depends on risk, interfaces, uncertainty and side effects, not just lines of code. Favor a representative end-to-end vertical slice early after authorized architecture approval.

## Compact formalization contract per level
`Goal -> verified inputs -> decisions (approved/proposed/unresolved) -> concise schema -> exit evidence -> next level`. Preserve provenance, source revisions, owner of decisions and invalidation scope. Return only to the earliest affected level when a defect or new fact requires correction; don't restart the entire process.

## Persistence without duplication
Proposed schemas live in existing task specification, optional immutable execution plan, log/handoff, conversation events/snapshots where warranted. Do not generate eleven documents or tasks by default. A separate supervision task is justified only for substantial independently tracked review; otherwise use an on-demand review pass. The current ai-workflow rules include system-design and generic execution methods, but have no fully specified development-phase workflow.

## Next design step
