Existing m-mk local-JSC example demonstrates source-side sibling project dependency but full actual integration acceptance remains open.

Proposed architecture: promote independently maintained TextEdit JS library and one shared browser renderer; two thin environment adapters (Electron main/preload IPC with contextIsolation, Node HTTP service with scoped authenticated file access) so browser and Electron share exact UI and editing behavior. Recommend separately installable `textedit-desktop` and `textedit-web` packages because Electron vs server dependencies, lifecycle and upgrades differ; library is a separate source project for mk and JSC. Stage one consumers embed compiled library artifact in installed packages, avoiding unimplemented JS loader package resolution; later explicitly test `pkg` installation of JS library as shared independently installed dependency. No need for mk/jsc on end-user runtime. Build/test/release: stabilize library and existing browser PoC, web app first, Electron next, two pkg builds/clean installs. Acceptance: parity of edit/render in both, open/save, test suite and clean runtime without source checkout, package dependency resolution. No changes to product repos this response.
